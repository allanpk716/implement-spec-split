# 任务：为地图实现票 <#a、#b…> 起草一份规格和它的执行票（只写草稿，不发布）

## 目标

仓库 `<仓库路径>`（GitHub `<owner/name>`）里，地图 #<地图号>「<地图标题>」下的实现票 <#a 标题、#b 标题…> 还没有规格。它们需要的决策已在地图的已关闭决策票里拍板。你要把这些决策综合成：

1. 一份规格正文 `<组目录>/spec.md`；
2. 这份规格拆出的执行票正文 `<组目录>/tickets/T1.md`、`T2.md`…；
3. 清单文件 `<组目录>/manifest.json`，格式见下文。

这一步只写草稿，由调用方审稿、问用户、再用脚本发布。**不要建票、评论、改标签，不对 GitHub 发任何写请求。**

## 先读

- 两个上游技能的规则和模板（以它们为准，下文只写本仓库的补充）：
  - 规格：`<to-spec SKILL.md 路径>`（模板、测试切入点要求、不写文件路径和代码片段）
  - 执行票：`<to-tickets SKILL.md 路径>`（竖切规则、阻塞边、issue 模板）
  - 两个技能里「问用户」的步骤你不做：要问的内容写进清单的 `seams` 和 `unresolved`，由调用方统一问。
- 目标仓库的 `CLAUDE.md`（写作规范）、`CONTEXT.md`（领域词）、`docs/adr/`、`docs/agents/issue-tracker.md`（规格与地图实现票的关联写法）。
- 地图和决策：`gh issue view <地图号> --comments`；地图下已关闭的决策票（`gh api repos/<owner/name>/issues/<地图号>/sub_issues`，挑带 `wayfinder:*` 标签、已关闭的），读每张的结论评论。
- 实现票本身：`gh issue view <n> --comments`。
- 风格参考：本仓库已有的一份规格和它的执行票，<规格号，如 #205>（`gh issue view`，执行票用 `gh api repos/<owner/name>/issues/<规格号>/sub_issues` 列出）。
- 相关代码：按需读，只为了找测试切入点、已有可复用的模块、需要先做的整理。

## 写作要求

- **只综合已拍板的东西。** `spec.md` 的每条实现决定后面用括号注明出处（`（#24 结论）`、`（地图 #22 Notes）`、`（实现票 #62 正文）`）。找不到出处、只能自己推断的决定，不写进正文，写进清单的 `unresolved`。
- `spec.md` 开头两行固定为：
  ```
  实现票：#a、#b
  地图：#<地图号>
  ```
  然后按 to-spec 模板写 `## Problem Statement` 等各节。
- 执行票按 to-tickets 的 issue 模板写。`## Parent` 下一行写 `#{{S<本组号>}}`，发布时会替换成规格票号；正文里提到本组别的执行票写 `#{{T2}}`，提到别组规格写 `#{{S2}}`。阻塞关系写进清单的 `blocked_by`，执行票正文里的 `## Blocked by` 一节照样写（用同样的占位符）。
- 执行票要用到 ssh-manager MCP、真机或远程服务器的（不能交给 codex worker 做的），在正文里写明「本票由 Opus 执行」。
- 用中文，遵守目标仓库的写作规范。

## manifest.json 格式

```json
{
  "key": "S<本组号>",
  "title": "规格标题",
  "body": "spec.md",
  "tickets": [
    {"key": "T1", "title": "执行票标题", "body": "tickets/T1.md", "blocked_by": []},
    {"key": "T2", "title": "…", "body": "tickets/T2.md", "blocked_by": ["T1", "S2", "#212"]}
  ],
  "unresolved": ["找不到出处或需要用户拍板的事项，每条一句，说明影响哪几张票"],
  "seams": "测试切入点：在哪一层测、复用哪些已有测试方式、需不需要新的切入点。两三句，给用户确认用"
}
```

`labels` 省略即可（默认 `ready-for-agent`）。`blocked_by` 的引用只能是本组的 `T<n>`、别组的 `S<n>`、或已有的 `#票号`。
