# 任务：为已有规格 #@@SPEC_NUM@@ 起草执行票（只写草稿，不发布）

## 目标

仓库 `@@REPO_PATH@@`（GitHub `@@REPO@@`）里的规格 #@@SPEC_NUM@@「@@SPEC_TITLE@@」已经写好，但还没有拆执行票。它覆盖地图 #@@MAP@@「@@MAP_TITLE@@」下的实现票 @@TICKETS@@。你要把这份规格拆成：

1. 执行票正文 `@@GROUP_DIR@@/tickets/T1.md`、`T2.md`…；
2. 清单文件 `@@GROUP_DIR@@/manifest.json`，格式见下文。

这一步只写草稿，由调用方审稿、问用户、再用脚本发布。**不要新建规格、建执行票、评论、改标签，不对 GitHub 发任何写请求。**

## 先读

- 上游技能的规则和模板（以它为准，下文只写本仓库的补充）：`@@TO_TICKETS@@`（竖切规则、阻塞边、issue 模板）。它里面「问用户」的步骤你不做：要问的内容写进清单的 `seams` 和 `unresolved`，由调用方统一问。
- 目标仓库的 `CLAUDE.md`（写作规范）、`CONTEXT.md`（领域词）、`docs/adr/`、`docs/agents/issue-tracker.md`（规格与地图实现票的关联写法）。
- 已有规格：`gh issue view @@SPEC_NUM@@ --comments`，逐节读。它的「实现票：」行指向 @@TICKET_NUMS@@；规格里的实现决定、Out of Scope 和测试切入点是拆票的主要依据。
- 实现票本身：`gh issue view <n> --comments`（逐张读 @@TICKET_NUMS@@），确认规格没有漏掉它们正文里的验收要求。实现票指向的已关闭决策票，若规格没有吸收结论，按未决处理，不要自行补规格。
- 必要时读地图 #@@MAP@@（`gh issue view @@MAP@@ --comments`）和相关代码，只为了确认拆分边界、测试切入点、已有可复用模块和命名习惯。

## 阻塞关系的规则

- 本组的执行票之间：`blocked_by` 写 `T<n>`。
- 必须等同批另一组完成：写那一组的规格 key（如 `S2`，表示等那份规格整体合并）。只给真正依赖它的执行票挂，能独立开工的部分不要挂。
- 仓库里已有的、还没关闭的**规格**或**有人在修的缺陷票**：写 `#票号`。
- **不要**挂在还没有规格的地图实现票上（例如另一张还在「缺规格」的 Web UI 实现票）：那样本规格要等对方的规格写完、实现完才能收尾。把依赖它的那部分执行票从本组拿掉，并在清单 `handoffs` 里给那张票留一条说明，让它写规格时纳入。
- 拿不准时按下文「未决的两种处理」处理，不要猜。

## 写作要求

- 执行票按 to-tickets 的 issue 模板写。`## Parent` 下一行写 `#{{@@KEY@@}}`，发布时会替换成 #@@SPEC_NUM@@；正文里提到本组别的执行票写 `#{{T<n>}}`（如 `#{{T2}}`），提到别组规格写 `#{{S<n>}}`（同批其他组的 key）。只有 `{{S<n>}}`、`{{T<n>}}`、`{{S<n>/T<n>}}`、`{{#<n>}}` 四种算占位符，其他花括号文本（例如产品自身的模板语法）原样保留。阻塞关系写进清单的 `blocked_by`，执行票正文里的 `## Blocked by` 一节照样写（用同样的占位符）。
- 拆分必须落在规格 #@@SPEC_NUM@@ 已写明的范围内。不要重写规格，也不要生成 `spec.md`；规格缺的信息按「未决的两种处理」上报。
- 每张执行票的验收标准要注明来自规格哪一节或实现票哪一段（如 `（规格 #@@SPEC_NUM@@ User Stories）`、`（实现票 #62 正文）`）。
- 执行票要用到 ssh-manager MCP、真机或远程服务器的（不能交给 codex worker 做的），在正文里写明「本票由 Opus 执行」。
- 用中文，遵守目标仓库的写作规范。

## 未决的两种处理

规格或实现票里找不到出处的事项分两种，不要一律写进 `unresolved`：

1. **实现者按现有习惯就能定的细节**（字段名、审计动作名、错误文案措辞、排序方式这类，仓库里有同类先例可循）：不进 `unresolved`。在执行票正文里写成「由实现者沿用现有 X 的习惯确定」，并点名那个先例。
2. **需要 owner 拍板的事项**（影响用户能看到的命令名或界面、安全语义、范围归属、拆分边界、阻塞关系）：写进 `unresolved`，每条必须带你的推荐答案，并写明采纳后要改草稿的哪几处，让调用方能直接照改。执行票先按推荐答案写，在该处加「（待确认）」。

## manifest.json 格式

```json
{
  "key": "@@KEY@@",
  "existing_spec": @@SPEC_NUM@@,
  "title": "@@SPEC_TITLE@@",
  "tickets": [
    {"key": "T1", "title": "执行票标题", "body": "tickets/T1.md", "blocked_by": []},
    {"key": "T2", "title": "…", "body": "tickets/T2.md", "blocked_by": ["T1", "S2", "#212"]}
  ],
  "unresolved": [
    {"question": "要 owner 拍板的问题，一句", "proposal": "推荐答案，一句", "affects": "采纳后要改的地方：T3 某条验收标准"}
  ],
  "handoffs": [
    {"issue": 84, "note": "交给那张票的说明：它写规格时要纳入什么、为什么，两三句；可以用 #{{@@KEY@@}} 指规格 #@@SPEC_NUM@@"}
  ],
  "seams": "测试切入点：在哪一层测、复用哪些已有测试方式、需不需要新的切入点。两三句，给用户确认用"
}
```

`existing_spec` 固定为 @@SPEC_NUM@@，`title` 固定为「@@SPEC_TITLE@@」，不要写 `body`。执行票的 `labels` 省略即可（默认 `ready-for-agent`）。`blocked_by` 的引用只能是本组的 `T<n>`、别组的 `S<n>`（不能是本组 @@KEY@@）、或已有的 `#票号`。没有 `unresolved` 或 `handoffs` 时写空数组。
