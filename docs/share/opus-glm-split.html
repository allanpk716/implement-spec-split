一次交接的完整流程 橙 = Opus · 蓝 = GLM

1
定方案、拆票 /grill · 规格 Spec · 执行票
和人把需求问清楚，写成规格，拆成票并标好依赖。/find-next --batch 把要拍板的问题合成一轮问人。
2
写自包含 Brief worker 看不到对话
写清目标、文件与行号、根因、改法、验收命令、禁区；写明“不要 commit”。
3
后台编码 codex-worker.sh → GLM-5.4
每张票独立 worktree，用 TDD 推进，可并行；progress.sh 查看进度，卡死自动判定；结束写 status.json 和 result.md。
4
验收与审查 不信 worker 的自述 · 不通过就写新 Brief 回到 ③
读 git diff，亲自重跑验收命令；合入后两路 Opus 审查：Standards（是否合规范）与 Spec（是否合规格）。
5
落地 对外动作只由 Opus 执行
commit → 持锁合入 main → push / PR → 关票，再自动开下一波规格。

护栏：靠机制，不靠自觉

硬拦截大改动PreToolUse hook delegate-guard：Opus 直接改源码超过 10 行即被拒，只能交给 worker。
对外动作不外包worker 以 bypass 模式运行、权限很大；push、PR、远程操作、删数据一律由 Opus 执行或先问人。
按状态码分流ok 照常审查 · quota/auth 先问人 · timeout 续跑一次 · stalled/error 补充 Brief 后重跑 · 只读调查改了文件 → 报告作废。
并行不打架每张票各自 worktree；合并串行；落地持仓库锁；MCP 默认关闭，按需开启。
