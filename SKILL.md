# implement-spec-split

Same goal and task-graph workflow as `mattpocock-skills:implement-spec`, with one difference: **models are chosen per role** instead of inherited from the session. The steps below are self-contained; do not invoke the original `implement-spec` (it runs its own review on the inherited model).

Terms (Orchestrator, External worker, Orca Run, Stage route, Lean start, Sidecar, Brief, ...) are defined in `GLOSSARY.md` next to this file.

## Usage

- `/implement-spec-split <spec ref> [--parallel N]`: implement or recover one Spec as described below. The spec ref is required. How the Tickets are implemented is not an option: every implementing role goes through `scripts/stage-dispatch.sh` on the Stage route table's 实现 route, the same in a flash session and in an official-subscription one (only the step-7 review differs, see "Flash mode"). The backend switch of earlier versions and its Progress tabs are retired (规格 #26; the MAINTAINING.md 设计要点 entry for 票 #45 names them). `--auto-land` turns the Run into an **Unattended landing** (see that section). find-next's launch commands (`launch-wave.sh`, including its `--only` and `--next-wave` paths) add it by default, so those Runs land unattended; `--no-auto-land` opts a batch out. Only a Run started by typing `/implement-spec-split <n>` without it still asks before pushing.
- `/implement-spec-split` without a spec ref: do not scan or list candidates. Say "先运行 `/find-next --batch`，它给出开发顺序和每个 worktree 要敲的命令" and stop. Choosing what to build happens in one place (find-next), so several worktrees started at once never scan and pick in parallel.
- `/implement-spec-split --status`: only run `<skill dir>/scripts/pipeline-status.sh`, relay its result, and stop. Do not take a Spec, run preflight, or dispatch a worker.

## Config (edit here to change the policy)

- **Implementation is dispatched, never chosen.** The implementing roles — a Ticket's implementer, the fix role and a merge-conflict role — always run as Orca workers started by `scripts/stage-dispatch.sh` on the 实现 route of the Stage route table, in every kind of session; the backend switch of earlier versions is retired (规格 #26). The user changes the route with `/grill-router`; the module reads the table afresh on every dispatch, so a change reaches the next Ticket and never a worker that is already running. Before 2026-11-28 the default path ran the implementing roles as in-session subagents, which had no exit script and so could never be switched.
- `GLM_MAX_PARALLEL` = `2` — at most this many implementation workers (the Orca workers dispatched for Tickets, a fix role or a conflict role) at once. Override per run with an argument: `/implement-spec-split <spec> --parallel 4`. The override replaces the default for that run only. It is per Run: parallel Runs on different Specs add up. Keep it small (2–3, at most 4 off-peak): Zhipu rate-limits during peak hours, and one quota/429 among the workers stops the whole run to ask the user. The machine-wide total is governed by find-next's workers ÷ specs split; an Orca worker takes no Worker slot (the headless exploration executor does, see "Headless executor").
- No Time limit or Idle timeout for an Orca worker: nothing runs it through a wrapper, so nothing kills it on a clock or on silence. `stage-dispatch.sh wait --timeout` (default 7200 s) only says how long one blocking wait lasts; on a timeout judge the worker by Orca's liveness and the Watchdog, never by the clock alone. The headless exploration executor keeps the wrapper's own budgets (`scripts/codex-worker.sh` header; the dispatch module passes none, so its defaults apply).
- Headless executor's model and reasoning effort: not a Config value (2026-11-27, ADR 0004). `codex-worker.sh` takes both from the Stage route table (`scripts/stage-route.sh`, the user's `/grill-router`): the `research` stage for the step-2 exploration, which is a `--read-only` dispatch; see "Stage route" under "Headless executor". Do not pass `--model` or `--thinking` to the wrapper. The endpoint and key belong to the user's provider setup, never in this repo (author environment: Ferryman, `127.0.0.1:15722`).
- `REVIEW_MODEL` = `opus` — every code-review subagent (use `fable` for the strongest option). Review always runs In-session (non-flash sessions only; in Flash mode every review runs out-of-session via `opus-review.sh`). Pass `model: REVIEW_MODEL` explicitly on every review Agent call; never rely on inheritance: the session itself may be on any model.

## Principles (from implement-spec)

- The goal is the entire spec implemented on a single **integration branch**, with every ticket resolved the way the issue tracker closes work.
- The tickets are a **task graph** with blocking relationships, not a list of steps. There is always a **frontier** of tickets ready to be grabbed.
- Start every subagent with a fresh context window, never a fork (a fork ignores the `model` override, so the per-role models would not apply).
- Communication to and from subagents should be sparse. Communicate through **context pointers** (spec, tickets, research notes, previous commits); don't duplicate information already available via pointers.
- Dispatch implementers in parallel where possible for maximum concurrency: each Orca worker runs by itself in its own worktree, and the session waits for it with one blocking `wait`, never a polling loop.

## Step 0: pick the spec and take it

Several Runs may work at once, one Spec each, typically one Claude Code session per worktree, all started from the order that `/find-next --batch` printed (it can also start those sessions in Orca itself). Here `<n>` is always the **Spec issue number**, not the number of a wayfinder map or map implementation ticket.

A Spec is taken when its integration branch `spec-<n>` exists. Whether the Run holding it is still alive is recorded in its **claim record** (GLOSSARY.md): `$(git rev-parse --git-common-dir)/implement-spec-split/claims/spec-<n>.json`, written and read only through `<skill dir>/scripts/claim.sh`. It stores the PID and start time of the Claude Code process that took the Spec, so liveness does not depend on Orca. `claim.sh status <n>` prints `free`, `active <record>` (the holder process is alive) or `interrupted <record|none>` (branch exists, holder gone or no record).

On GitHub, identify Specs structurally, not by a “规格：” title prefix:

- A current Spec is an open issue whose body contains the to-spec template heading `## Problem Statement`.
- A legacy Spec is an open parent issue without the `wayfinder:map` label and without that heading, but with unfinished sub-issues.

Resolve a Spec to its Tickets in this order:

1. If the Spec issue has its own sub-issues, those sub-issues are the Tickets.
2. Otherwise, take the open wayfinder map implementation tickets referenced on an `实现票：#<n>` (also `实现票为 #<n>`) or `Implementation ticket(s): #<n>` line in the Spec body (only that line counts: specs also mention other map tickets as out of scope, and those must not be collected). to-spec does not write this line by itself, so the repo's tracker doc should require it. Such an implementation ticket has no `wayfinder:*` label and belongs to a `wayfinder:map` issue. If it has sub-issues, those sub-issues are the Tickets; if it has none, that implementation ticket is itself the one Ticket (a single-ticket Spec). Multiple referenced implementation tickets are all collected.

1. **Verify the ref.** It must meet one of the Spec rules above; otherwise say so and stop.
2. **Take it atomically**, from any directory inside the repo:

   ```bash
   <skill dir>/scripts/claim.sh take <n>
   ```

   It creates branch `spec-<n>` with its worktree at `<repo parent>/<repo>-wt/spec-<n>` from the main branch and writes the claim record, under a short repo-wide lock so two sessions cannot both pass the check. Exit 0 prints the worktree path: that is the integration worktree. Exit 3 means the Spec is already taken; the output says whether it is `active` or `interrupted`:
   - `active`: another live Run holds it, or find-next has reserved it for a session it is starting. Tell the user which worktree, and stop. Never work on it in parallel.
   - `interrupted`: this is **Recovery** (GLOSSARY.md). Ask the user to confirm, then `claim.sh resume <n>` (rewrites the record with this session as holder) and continue under "Recovery" below.

   When find-next started this session (`launch-wave.sh`), it reserved the Spec first (a **handoff reservation**, GLOSSARY.md) and this session already runs inside the Spec's worktree on branch `spec-<n>`. `take` then adopts the reservation instead of creating anything: exit 0 prints the current directory, which is the integration worktree (a fresh Spec); exit 4 prints it too and means Recovery that find-next already decided on, so continue under "Recovery" without asking again.
3. **Blocked Spec.** If every open ticket is blocked by tickets outside this Spec that are not merged into the main branch yet (its frontier is empty), say what blocks it, `claim.sh release <n>`, remove the just-created worktree and branch if they have no commits, and stop.
4. In Orca (`ORCA_WORKTREE_ID` set and `orca` on PATH), also mark the session for the user: `orca worktree set --worktree current --issue <n> --workspace-status in-progress` and `orca terminal rename --title "spec-<n> <short title>"`. This is display only; the claim record is what other Runs and find-next read.
5. Exactly one Spec per Run. `--parallel` / `GLM_MAX_PARALLEL` caps this Run's concurrently dispatched implementation workers (Ticket implementers, fix and conflict roles); see "Config".
6. Create the Orca Run this Run's Ticket workers report into (GLOSSARY.md "Orca Run"; the dispatch module names it explicitly on every call and never inherits one from the terminal), and run the headless executor's preflight ("Headless executor"), before any other work. In Orca (`orca` on PATH):

   ```bash
   orca orchestration run-create --objective "spec-<n> Ticket workers" --json
   ```

   Keep its id (`result.id`, else `result.runId`) in `<Spec Run root>/orca-run-id`: every `stage-dispatch.sh dispatch --stage implementation` takes it as `--run`. The implementing roles are Orca workers, so a session without Orca cannot dispatch them: say so and stop. If this session's terminal is ever replaced, the new one takes the Run over with `orca orchestration run-use --id <run id>` before dispatching or waiting again.

### Tickets blocked by another Spec

Some open tickets may be blocked by tickets that belong to another Spec (or a standalone issue) not yet merged into the main branch, or may be `ready-for-human` tickets, which are never dispatched. Build only the rest. Never implement the other Spec's scope inside this one, not even a "small shared helper": that is how one judgement got written twice in #222 and #223. Leave those tickets open, finish and land the rest, keep this Spec open, and say in the final report which tickets wait for which Spec (`剩余：#<t> 等 #<spec>`) and which wait for a human (`等人工票 #<t>`). This is a **partial landing** (step 10): it ends the Run cleanly and is never a reason to park.

If you need to know whether the blocking Spec is being worked on, check it fresh at that moment with `claim.sh status <m>` together with the issue state. Never conclude "nobody is working on it" from the issue being open, and never reuse what you saw in step 0.

### Recovery

**Clock first.** When resuming this Run, continuing after `/clear`, or judging how long a role or process has run and whether it is still alive, run `date` first for the current time, then `ps -o pid,etime,time,command -p <pid>` for the process's elapsed time (`etime`) and CPU time (`time`); never derive a duration from clock times found in logs. A process whose elapsed time is long while its CPU time is near zero is stalled — treat it as stuck, not as working.

Never read `run.json`: it is display-only and may be stale or missing. GitHub, Orca and the worktrees are the only source of truth. Continue the Spec on its existing integration branch and integration worktree (`git worktree list` shows where `spec-<n>` is checked out). Closed tickets count as already merged; only the open ones form the frontier. Take the Orca Run over as step 0 says when the terminal changed (`orca-run-id` in the newest run dir names it). Then, for each dispatch the earlier Run left behind (the `dispatch-*.json` sidecars of the newest run dir under `~/.cache/implement-spec-split/runs/<repo>-<n>-*/`; `git worktree list` shows the ticket worktrees `spec-<n>-t<m>`):

- a sidecar with a `worker_done` recorded: the worker finished and its report is at `worker_done.report_path`. Verify it (the gate under "Dispatching a role"), merge it (step 5) and release it.
- a sidecar with a `dispatch_id` but no `worker_done`: ask Orca, `orca orchestration worker-show --dispatch <id> --json`. `liveness: live` → it is still running: `stage-dispatch.sh wait --sidecar <file>` for it, never stop it. `liveness: exited` → it ended without reporting: treat that role as `error`. A ticket branch with commits still goes through the gate and the merge (step 5) — the work is what matters, not who reported it — and since `release` refuses a dispatch without a `worker_done`, remove its worktree by hand after the merge (the next bullet); a ticket worktree without commits is removed the same way and the ticket dispatched afresh. `unverifiable`, or an Orca that cannot answer: do not stop or re-dispatch it on a guess (Orca forbids both on anything but an exited worker); re-arm the Watchdog and say so in the report — an unattended Run parks with category `error`.
- a sidecar without `dispatch_id`, or a worktree to be removed by hand: the dispatch did not complete or cannot be released; its sidecar names whatever was created. Close the terminal and remove the child worktree by hand — `orca terminal close --terminal <terminal> --tab`, `orca worktree rm --worktree path:<worktree> --force --delete-branch` (a ticket worktree only, never the Spec worktree) — then dispatch afresh.

## Steps

**Phase marks.** At each phase change run `<skill dir>/scripts/run-phase.sh <phase> --repo <repo> --spec <n> --wave <w> --merged <a> --in-progress <b> --todo <c>` (`<w>` from the launch state if known; counts from the frontier). It writes `run.json` in the Spec's Run directory for the Progress board only; a failed write just warns, so never act on its output. Phases: `split`, `implement`, `integrate`, `review`, `land`, `waiting`, `parked`, `done`.

**Run directory.** `<Spec Run root>` is `~/.cache/implement-spec-split/runs/<repo>-<n>-<YYYYmmdd-HHMM>/` (`<repo>` = the main checkout's directory name; `run-phase.sh` writes `run.json` there, so Recovery finds it). It lies outside every worktree, and it is the `--run-dir` of every dispatch: each writes its files under `<Spec Run root>/<name>/` and its Sidecar (GLOSSARY.md) as `<Spec Run root>/dispatch-<name>.json`, where `<name>` is the role and its ticket (`implement-<m>`, `fix`, `merge-<m>`, `research`; a re-brief appends `-2`, `-3`…). Briefs go under `<Spec Run root>/briefs/`. The dispatch module refuses a run directory inside the Spec worktree, since release removes that worktree.

"Dispatch <role>" below means one `stage-dispatch.sh dispatch --stage implementation` call (see "Dispatching a role"): an Orca worker in a worktree, started on the 实现 route, in every kind of session. The session starts a worker no other way — not an in-session subagent for an implementing role, not `codex-worker.sh` (that is the headless executor of the step-2 exploration), not `orca orchestration worker-start` or `orca terminal create` by hand — and writes no source itself.

**Implementing roles do not re-delegate.** The implementer, fix and conflict roles are Orca workers: they write the code and make the commits themselves in the worktree the dispatch module gave them, and they never start another worker (`codex`, `claude`, `claude-glm`, or `orca orchestration worker-start`) or an in-session subagent — the module's Task says so and every Brief repeats it. If a hook blocks a worker, it stops and states that in its report. Deterministic formatting commands (`gofmt -w`, `goimports -w`, `go fmt`) do not count as writing source: a worker runs them directly instead of dispatching a worker for them. No role starts a background process and then ends its turn to wait for a notification; if it must wait, it waits in the foreground with a sufficient timeout. A Lean start loads no hooks, so for such a worker these are prompt rules, backed by the gate before a merge and by review (step 7), not by a hook: write every rule it must keep into its Brief.

**No unresolvable `rm`.** Claude Code asks for confirmation, even under `--dangerously-skip-permissions`, when a Bash command contains an `rm` it cannot resolve statically; an unattended Run then sits at that prompt until a human answers (on 2026-11-24 a spec-18 implementer blocked 45+ minutes on `rm -rf "$S/stage"` inside a compound command that also passed `rm -f` to a wrapper script). Every Brief carries this rule verbatim (`find-next/templates/brief-implement.md` has it), and so does the exploration Brief: “Run any `rm` as its own Bash command with literal paths: no variables, globs, `$(...)`, or `sh -c` strings, and never chained with `&&`, `;` or pipes. Do not pass `rm` as an argument to a wrapper script; call `docker rm <name>` directly. Prefer fresh directory names over deleting and recreating one.”

**Progress is Orca's sidebar.** A Ticket's worktree is a child of the Spec worktree and its worker runs in a terminal of that worktree, titled `spec-<n> t<m>` (an implementer), `spec-<n> merge t<m>` (a conflict role) or `spec-<n> fix`; the sidebar shows them collapsed under the Spec, and `release` closes the terminal and removes the ticket worktree with its branch once the Ticket is merged (step 5), so the sidebar keeps nothing that is done. Open no tab yourself and keep no tab record: the progress tabs of earlier versions are retired (规格 #26); the sidebar is the progress view.

**Watchdog.** After dispatching any implementing role (implementer, fix, or conflict role), if no watchdog is running for this Run, start one with Bash `run_in_background: true`:

```bash
<skill dir>/scripts/run-watchdog.sh --watch <worktree>[=<dispatch dir>] [--watch ...] \
  [--stall 2700] [--interval 300] [--max 7200]
```

Pass one `--watch` per currently running role: the worktree it changes (the integration worktree for fix and conflict roles), with `=<dispatch dir>` appended. Set the Bash `timeout` to `(--max + 600) × 1000` ms. When new roles are dispatched, stop the old watchdog and start a fresh one over the new set. When its completion notification arrives, read the exit code and the lines it printed:

- `0` (every watched worktree is gone) or `2` (still progressing at `--max`): if any role is still running, start another watchdog.
- `3` (no fingerprint progress for `--stall`): ask Orca first, `orca orchestration worker-show --dispatch <id> --json` (the sidecar has the id). `liveness: live` → re-arm the watchdog: a worker may think long before it touches a file. `liveness: exited` → the role ended: its `wait` returns its `worker_done`, or the Recovery rules apply when it has none. `unverifiable`, or an Orca that cannot answer → do not stop or re-dispatch it on a guess (Orca forbids both on anything but an exited worker): re-arm once, and if the next report flags the same role again, say so in the report (an unattended Run parks with category `error`, naming the dispatch id). A role Orca calls `live` that the next report flags again with no progress is stalled: stop it (`orca orchestration worker-stop --dispatch <id>`), clean up its dispatch by hand as Recovery describes (it never sent a `worker_done`, so `release` refuses it), and dispatch it again with `--attempt 2`; count it toward the consecutive-failure rules (the Unattended-landing and Flash-mode second-failure rules below still apply).

1. Mark `split` (run-phase.sh), then read the spec and tickets and compute the frontier. The issue tracker comes from the repo's `docs/agents/issue-tracker.md`; if missing, tell the user to run `/setup-matt-pocock-skills`. **The frontier comes only from `scripts/frontier.sh`**, never from your own reading:

   ```bash
   <skill dir>/scripts/frontier.sh --repo <owner/name> --spec <n>
   ```

   The ticket numbers printed before the first `# ` heading are the frontier, one per line; `# blocked` lists blocked tickets with their open blockers; `# human` lists `ready-for-human` tickets (never dispatch those); `# shelved` lists shelved ones. The script applies the Spec-to-Ticket resolution rules in step 0 (including a single-ticket Spec whose only Ticket is the referenced map implementation ticket) and reads the tracker's blocking relationships (`dependencies/blocked_by`). A ticket with any open blocker is not in the frontier, whatever the code or ticket text seems to say; never build the graph from your own reading of which code a ticket needs, and do not query `blocked_by` yourself to second-guess the script. **If the script fails** (non-zero exit), wait 30 seconds and run it once more; if it fails again, park with category `transient` (see the Park section). If you believe an edge is wrong or missing, say so in the final report and leave the edge as it is; do not implement around it (on 2026-11-25 a flash Run on proxy-hub Spec #21 drew its own dependency table from the code, judged #44 "only needs Spec ①", and landed it while its blockers #40 and #42 were still open).
2. Dispatch the exploration: once per Spec, before the first implementer, never optional — every Ticket's Brief carries what it writes. It is headless and read-only: `<skill dir>/scripts/stage-dispatch.sh dispatch --stage research --brief <Spec Run root>/briefs/research.md --run-dir <Spec Run root> --cwd <integration worktree>` hands it to `codex-worker.sh --read-only` on the 调研起草 route (see "Headless executor"; in Flash mode prefix that one command with `WORKER_ALLOW_FLASH=1`). Write its Brief fresh: the Spec issue number, the Ticket numbers with a line each, and what the notes must hold — for every Ticket the files it touches with `file:line` and why, the call relations in and out of them (`function (file:line) -> …`), the repo's real test commands, and anything an implementer must not break — to be written to `<Spec Run root>/research/notes.md` (the dispatch dir, outside the repo), where every later Brief reads them; it must not modify the repo. Gate: exit `0`, `status.json` says `read_only_violation` is false, and the notes exist. Exit `8` (a read-only violation: it changed the worktree) voids the notes: inspect `status.json`'s `changed_paths`, revert the changes by hand, and dispatch it again with `--attempt 2`. The other exit codes are the executor's ("Headless executor").
3. The integration branch `spec-<n>` and its worktree were created in step 0; merges (the script, and a conflict role) and the final steps run in that worktree, never in the session's own directory. If the issue tracker closes work through PRs, or the user asks for one, open a draft PR after the first merge in step 5 (a branch with no commits ahead of main can't open one), marked as closing the spec and tickets.
4. Mark `implement`, then dispatch one implementer per frontier ticket, each with one command: `stage-dispatch.sh dispatch --stage implementation --role implement --ticket <m> …` (the full form under "Dispatching a role") gives it a child worktree of the Spec worktree, on branch `spec-<n>-t<m>` off the integration branch, filed under the ticket in Orca. Write its Brief from `find-next/templates/brief-implement.md`: products only — the Spec issue's content, the exploration notes that concern this Ticket (the files and call relations), and the Ticket issue's content — never this session's process. Dispatch as many as `--parallel` / `GLM_MAX_PARALLEL` allows and wait for each (step 5). If a git command fails on an existing `.lock` file (parallel Runs share one repository; the Brief tells the worker the same), wait a few seconds and retry, at most 3 times; never delete `.lock` files. An **ops ticket** (see [Ops tickets](#ops-tickets)) is the exception: no TDD and no commit required, and its verification gate is the ticket's acceptance criteria. Each implementer (the Brief says so):
   - confirms its worktree is based on the integration branch before starting, and resets onto it if not;
   - builds the ticket test-first (the tdd rules travel in the Brief — a Lean start loads no skills, so the Skill tool is not how they get there; see "Lean start");
   - commits on its own branch and leaves no uncommitted changes. It merges no other branch, not even the integration tip: merging is step 5's, by script, and a conflict is a merge role's.
5. When an implementer's `wait` returns (exit 0: its report path), mark `integrate` (re-mark `implement` if tickets remain), verify it (the gate under "Dispatching a role"), then **merge with the script first**: the script is the merger, and a worker is dispatched only on a conflict.

   ```bash
   <skill dir>/scripts/merge-ticket.sh --worktree <integration worktree> --integration spec-<n> \
     --ticket spec-<n>-t<m> --test '<the repo's test command>'
   ```

   It merges in the integration worktree (`--no-ff`) and runs the test command there; its gate (new commits on the ticket branch, a clean ticket worktree and a clean integration worktree) runs before anything is merged. By its exit code:
   - `0` (merged, tests passed): release the implementer — `<skill dir>/scripts/stage-dispatch.sh release --sidecar <its sidecar>` does `worker-release`, closes its terminal and removes the ticket worktree with its branch, so the sidebar keeps no merged Ticket — then step 6.
   - `3` (a conflict; the worktree is back to the pre-merge state and stderr names the conflicted paths): dispatch a merge role — `--role merge --ticket <m>`, one command as above; it works in the integration worktree on the integration branch and always starts normally, never lean, since a conflict resolution is the riskiest work a worker does here — with a Brief naming those paths and both sides' intent, `wait` for it, then run the test command in the integration worktree yourself (the merge is already committed, so `merge-ticket.sh` would exit 5), release both dispatches (the merge role's too: for it, release only closes its terminal), and step 6.
   - `2` (gate not met; stderr says which check): a dirty integration worktree is the session's own to clean (never a reason to release a worker); any ticket-side miss — no new commits, a dirty ticket worktree, a branch nobody has checked out — means the implementer's work is incomplete: release it (which drops the worktree and its branch) and re-dispatch the ticket with `--attempt 2` and a Brief that says what was missing; a second miss is a failed gate (the Unattended-landing rules).
   - `5` (the Ticket branch is already part of the integration branch, behind a merge commit: the ticket has landed; nothing merged, stderr says so — a Recovery re-run of this step, or a worker that merged its own branch): release the implementer (as for `0`: the worktree and its branch go with it) and go on to step 6. Do not dispatch the ticket again: there is nothing left to implement.
   - `4` (merged, but the tests failed; the merge commit stays): dispatch a fix role with the failure output (step 8's form), at most 2 rounds, then park.
   - `1` (a git failure; stderr says which): resolve by hand, or park with category `error`.

   For Go repos, the test command also cross-compiles for the other platforms CI builds (`CGO_ENABLED=0 GOOS=linux go vet ./...` and `CGO_ENABLED=0 GOOS=darwin go vet ./...`, or `GOOS=windows` when running on Linux/macOS). A local suite only proves the host platform: files named `*_windows.go` / `*_linux.go` etc. are silently excluded elsewhere, so a green local run can hide a red CI lane. **Run one merge at a time**; queue the rest.
6. If this changes the frontier, recompute it with `frontier.sh --repo <owner/name> --spec <n>` (step 1; the same retry-once rule applies) and dispatch implementers for the newly unblocked tickets it lists, and for nothing else. Never promote a ticket because the code or the ticket text suggests its blockers are done.
7. **Review (the split point).** Mark `review`. When all tickets are merged (except those waiting for another Spec or a `ready-for-human` ticket, see "Tickets blocked by another Spec"), call the Skill tool with `mattpocock-skills:code-review` (not the built-in `code-review`, which does not spawn the two axis sub-agents) on the integration branch, using the branch point from the main branch as the fixed point. When it spawns the Standards and Spec sub-agents, set `model: REVIEW_MODEL` on both. Do not skip this step, do not downgrade the model, and never hand review to an External worker. In Flash mode, see "Flash mode".
8. Save the review report to a file outside the repo (`<Spec Run root>/review-<k>.md`) and dispatch a single fix role with that file as its context pointer: one command, `stage-dispatch.sh dispatch --stage implementation --role fix …` (no `--ticket`; it works in the integration worktree on the integration branch), record the pre-fix tip, `wait` for it, apply the gate (new commits on `spec-<n>` since that tip, a clean integration worktree, the test command passing there), then release its sidecar when the fix role ends, whatever the outcome (release closes its terminal; the worktree stays). ## Ops tickets

An execution ticket is an **ops ticket** when its body says it is carried out through ssh-manager, it has a `## 护栏` section, or it carries the `ops` label. Ops tickets are still dispatched to an implementer, with these differences:

- **MCP**: the dispatch takes `--mcp-config <file>`, an MCP config JSON naming `ssh-manager` (the dispatch module passes it to the launcher on a Lean start and on a normal one alike). The Brief says the worker may use the `mcp__ssh-manager__*` tools — call `mcp__ssh-manager__list_servers` first for the real `server_id` and read that server's `caveats` / `role` / `services` before acting — and copies the ticket's `## 护栏` section verbatim. The Brief template's ops section holds both. (`--bare` with a non-empty `--mcp-config` is one of #39's verification items; until it is settled, the sidecar's `bare_note` says which start the worker got.)
- **Guardrails and acceptance**: when the implementer would have to break a guardrail, or the ticket's acceptance criteria cannot be met, it only reports — it never pushes through. The main session parks with category `error`, and the parking report includes the rollback steps (what was changed on the remote host and how to undo it).
- **No TDD, no commit required**: an ops ticket is not built test-first and does not need a commit. When it changes no code, the implementer's verification gate becomes "every acceptance criterion on the ticket has evidence" (command output, service status, a screenshot), not the new-commits / clean-tree checks: such a branch has no commits, so step 5's script is skipped for it — release the implementer (which removes its worktree) and close the Ticket on its evidence.

`ready-for-human` tickets are never dispatched, ops or not: `frontier.sh` keeps them out of the frontier and lists them under `# human`, and `pipeline-status.sh --all` reports them as `人工票待做：#n`.

## Unattended landing (`--auto-land`)

This batch lands without the user, typically to run overnight: `launch-wave.sh` starts every Run with `--auto-land` by default (`--no-auto-land` opts a batch out), so nobody will answer a question, and by morning this session's cache has expired, so waiting costs tokens and gains nothing. A Run started by typing `/implement-spec-split <n>` without `--auto-land` is not unattended and keeps its confirmations. Two rules decide everything here: save tokens, and never sit waiting for a person. Wherever this file says "ask the user", "tell the user" or "confirm", apply the matching rule below instead; anything not listed means **park** (see below).

- **Watchdog**: the Watchdog rule in Steps is mandatory here — keep one running after every dispatch of an implementing role; an unattended session must never sit waiting only for notifications.
- **Landing (step 9)**: no confirmation.
- **Design-level review items (step 8)**: resolve them yourself when the Spec, its tickets or an ADR already answer them, and record each decision in the landing report. Otherwise every item under `## 需要人取舍` is decided here and **never parks the Run for being a trade-off** — `可自动采纳：否` is the reviewer's honest mark that a human would have had to choose, not a reason to stop:
  - An item with a recommendation and `可自动采纳：是` is **auto-decided**: apply the recommended option (one fix role for all of them, after the mechanical fixes), and list each under `### 自动拍板（可推翻）` in the landing report: the question in one line, the option taken, the rejected options, and the commit.
  - An item marked `可自动采纳：否` or `推荐：无` is decided by the **Reversibility rule**: pick a reversible option by 「可逆性高 > 改动面小 > 与现有 ADR 一致」, preferring the reviewer's recommendation when it is reversible and not outward-facing, and record it the same way, with the reason. In Flash mode this choice goes to one Opus review (see "Step 8 findings"), whose recommendation the Run applies. Owner decision 2026-11-25: in the proxy-hub Runs the user picked the recommended option in 10 of 11 such items, and the one exception had no recommendation, so parking for them only cost a night.
  - An item whose reason is an action that needs the owner's identity or credentials (a first login, a payment, a verification code) parks with category `auth`.
  - An item whose listed options hold nothing reversible parks with category `error`; never invent an option.
  - An option that loosens a safety boundary is never taken, whatever the rule above would pick: record it under 「未执行的放宽项」 in the landing report and decide among the remaining options as above.

  Release that fix role when it ends. The step-8 review-round cap applies unchanged: at most 3 review → fix → re-review rounds per review stream; after the third, mechanical-only leftovers land and are reported, and any correctness leftover parks with category `error`.
- **Follow-up tickets (step 9)**: a leftover or cleanup ticket opened while landing is attached to the Spec, has each of its dependencies registered with `blocked_by`, and leaves the Spec open as a partial landing. Never write dependencies only into a title, and never close the Spec on top of such tickets (on 2026-11-25 spec-22 left #50/#51/#52 as loose issues that the tracker still called ready).
- **Main merge (step 9.1)**: conflicts — dispatch a fix role to resolve them, then run one `REVIEW_MODEL` review of the conflict resolution only (`mattpocock-skills:code-review` with the pre-merge `spec-<n>` tip as fixed point); clean → continue, findings → one fix role, then continue if green. Failing tests after the merge — dispatch a fix role with the failure output, at most 2 rounds, then park. Release each of these roles when it ends.
- **PR path**: instead of only marking the PR ready, mark it ready, wait for its checks (`gh pr checks <pr> --watch`, in the background), then `gh pr merge <pr> --merge`. Red CI — read the failing logs (`gh run view <id> --log-failed | tail`), dispatch a fix role, push, watch again; at most 2 fix rounds, then park. After the merge, close tickets/Spec as for a direct landing and run step 9.5 as if step 2's push had succeeded. Release the fix role when it ends.
- **Landing lock held over 30 minutes by another live Run**: keep waiting, do not take it over; after 2 hours, park with category `transient` and 可恢复时间 = the current time + 30 minutes (keeper resumes the Run then: nothing was changed, so waiting another round is the most reversible choice).
- **Worker failures**. An Orca worker: a `worker_done` whose outcome is `failed` (read the report: one that names quota or a 429 counts as `quota` below), a dispatch that ended without reporting (Recovery), or a failed gate — re-dispatch once with `--attempt 2` and a Brief that says what went wrong; a second failure parks. The headless executor's exit codes (the wrapper's header): `transient` — wait 10 minutes (`sleep 600` in the background) and re-brief once; a second failure parks. `quota` — stop dispatching, let running workers finish, then every 30 minutes run the executor's preflight in the background (`sleep 1800 && <preflight>`); when it passes, continue where you were; after 5 hours, park. `auth` — park. Second `timeout`, second `error`/`stalled`, or a second read-only violation — park (no third attempt). There is no other backend to switch to.

**Park** = post a **Parking report** (GLOSSARY.md) on the Spec issue with `gh issue comment`. Parking is for a Run that truly cannot go on — quota, an external service down, an action that needs the owner's identity or credentials, a correctness problem still open after three review rounds — never for a trade-off waiting for an answer: step 8 decides those. Parking means this Run stops here: for categories `quota` and `transient` the keeper daemon resumes it automatically after the stated 可恢复时间, for `auth` and `error` a human must act first. Tickets waiting for another Spec are a partial landing (step 10), never parking. The report has a fixed shape, because find-next's supervisor reads its first section and keeper reads the two machine-readable lines:

```
## 停车报告
停车类别：error
可恢复时间：无

### 需要你决定
1. <what is wrong, in one or two lines>
   A. <option> — <cost>
   B. <option> — <cost>
   建议：<option> — <reason>（或「无建议：<why>」）
（a `quota`, `transient` or `auth` stop instead names the one thing that happens next, or the one action only the owner can take, e.g. "GLM 额度用完，可恢复时间 2026-11-26T07:00:00+08:00，keeper 会自动恢复，无需回『继续』" or "需要你本人登录 X 完成授权，之后总控才会恢复"）

### 现状
<what is already merged into spec-<n>, tests, branch, run dirs>
<the output of `<skill dir>/scripts/stage-dispatch.sh verify --run-dir <Spec Run root>`, pasted as it is: the Stage route table and one check line per Orca worker of this Run>
```

The two lines right after `## 停车报告` are mandatory and come before `### 需要你决定`:

- `停车类别：quota|transient|auth|error`
- `可恢复时间：<ISO 8601 含时区>|无`

`### 现状` also carries the route table and the check lines — the output of `stage-dispatch.sh verify --run-dir <Spec Run root>`, pasted as it is: a park is exactly when the user needs to know who wrote and who reviewed, and a worker still running (a parked Ticket's) is read live by that command. A line that says 警告 (the worker ran another model than its route) or 无法核对 is pasted as it is; it never held back anything. All of it goes under `### 现状`, so the first section the supervisor relays verbatim and the two machine-readable lines keeper reads are untouched.

| 类别 | 场景 | 可恢复时间 |
|---|---|---|
| `quota` | 额度用尽或 429 | 额度重置时刻；不知道就填当前时间 + 5 小时 |
| `transient` | 网络或端点临时错误；落地锁被别的 Run 占超过 2 小时 | 当前时间 + 30 分钟 |
| `auth` | 需要本人身份或凭据的操作：首次登录授权、付款、验证码 | `无` |
| `error` | 重复失败、验收不过、三轮审查后仍有正确性问题、护栏违反；取舍列出的选项里没有可逆的；`opus-review.sh` 非 0 退出且不是 2 / 3 / 4 | `无` |

`decision` and `other` are retired: a trade-off is decided by the step-8 rule, never parked on. keeper (`scripts/keeper.sh`) reads these two lines and resumes `quota` and `transient` parks automatically once 可恢复时间 has passed, so "额度用尽" is never written as "等人恢复" any more. `auth` and `error` still need a human: keeper notifies once per report and never resumes them, whatever 可恢复时间 says.

No other wording for the next step ("回 find-next 选『先恢复』" and the like): find-next's supervisor handles the report. An item with a recommendation it decides itself, writing the answer back as a `## 拍板` comment (marked 总控自动拍板, 可推翻) and restarting the Run with `launch-wave.sh --only <n> --apply`; only an item that needs the owner's identity or credentials (category `auth`) is asked of the user, whose answer is written back the same way. Mark `parked`, then release the landing lock if held, let running workers finish or leave them (Recovery handles them), do step 10 except that the Orca status is `in-review` and the tab `spec-<n> ⏸`, and end the Run. Do not run step 9.5. Other Specs of the batch carry on independently.

**Resuming after parking**: in Recovery, read the Spec issue's comments; the newest `## 拍板` comment after the newest `## 停车报告` holds the answers — the user's or the supervisor's auto-decisions, which count the same. Apply them (one fix role for all answers, then step 7's review only of that fix; release it when it ends) and continue to landing. The `## 拍板` answers count as authorised for this Run: do not park on the same items again.

**Landing report**: after a successful unattended landing, post the final report (below) on the Spec issue as `## 落地报告`, condensed but in the same order as "Report at the end" (completion.txt verbatim, then the `## 结论` block with 要你做的, then details): tickets landed, review findings and how each was resolved, `### 自动拍板（可推翻）` (each item's question, option taken, rejected options, commit, and the reason where the Reversibility rule picked it; omit when empty), 「未执行的放宽项」 (omit when empty), tickets left waiting for another Spec (`剩余：#<t> 等 #<spec>`, one line each), the Specs step 9.5 started, and the route table with the check lines — completion.txt already ends with them when it ran with `--run-dir`; when it did not, paste `stage-dispatch.sh verify --run-dir <Spec Run root>` instead. The user reads it through find-next's supervisor or GitHub, not by reopening this session.


### spec-keeper (the daemon that resumes unattended Runs)

launchd runs `scripts/keeper.sh` every 10 minutes (service in `~/ops/services/spec-keeper/`) for repositories whose launch state does not set `auto_land` to false:

- a parking report with `停车类别：quota|transient` whose `可恢复时间` has passed → `launch-wave --only <n> --apply`;
- a claim that turned `interrupted` with no newer report → it asks Orca the same way first, since the session may still be working in the worktree (a resume would double it): `live` → left alone and notified once per Spec; `exited`, or no worker listed for the worktree at all → a confirmed death, it closes the terminal Orca has not released and resumes through the same claim; `unverifiable`, or an Orca that cannot answer → notified once per Spec and evidence, never resumed on a guess (a Spec whose worktree is gone has nothing to be live in: resumed without asking);
- a claim still `active` with no write to the session transcript (subagents included), the Run directory or the worker run directories for 45 minutes → it asks Orca for the worker in the Spec worktree (`worker-list`, then `worker-show`): `live` → left alone, however old the files are (no 「继续」, nothing closed, nothing relaunched); `exited` → a confirmed failure, it closes the terminal Orca has not released, force-releases the claim and resumes; `unverifiable`, or no worker listed for the worktree, or an Orca that cannot answer → notified once per Spec and evidence, never resumed on a guess (Orca forbids a stop, a retry or a release on anything but an exited worker);
- `auth` / `error` parks are only notified, once per report, and never resumed.

At most 3 automatic resumes per Spec per 24 hours, then it only notifies. Write the two machine-readable lines of every Parking report correctly: they decide whether the Run comes back by itself.

## Flash mode (`FLASH_ORCHESTRATOR=1`)

This mode is for a flash Orchestrator: the session itself is GLM, so a subagent named `opus` is not an Opus review. The rules below replace the matching step 7–9, worker-retry, and Unattended-landing rules when both apply; behavior not listed here is unchanged.

- **Dispatch**: implementation, fix and conflict resolution go through the dispatch module exactly as in any other session — there is no in-session path to choose and nothing to opt into. delegate-guard keeps the flash session itself from writing source; the workers it dispatches write it in their own worktrees (a Lean start loads no hooks, so the Brief carries the rules; a normal start loads them). Copy this rule verbatim into every Brief: “If a source-write hook blocks you, stop and state that in your report. Do not work around it: do not use `env -u FLASH_ORCHESTRATOR`, do not start another `claude`, `claude-glm`, or `codex` process, do not use `orca orchestration worker-start`, and do not write source through Bash to bypass the hook.” The headless executor (`codex-worker.sh`) refuses to start under `FLASH_ORCHESTRATOR=1` without `WORKER_ALLOW_FLASH=1`: set it for step 2's exploration dispatch and for nothing else (`WORKER_ALLOW_FLASH=1 <skill dir>/scripts/stage-dispatch.sh dispatch --stage research …`). Never set it otherwise, and never start a worker outside this skill.
- **Step 7 review**: do not call `mattpocock-skills:code-review` in the session and do not spawn an `opus` subagent. Compute the integration branch's fork point from the main branch (`git merge-base <main branch> spec-<n>`) and run:

  ```bash
  <skill dir>/scripts/opus-review.sh --kind code \
    --input <fork-point commit> --out <run dir>/opus-code-review.md \
    --cwd <integration worktree>
  ```

  Save and use that findings file for step 8.
- **Step 8 findings**: mechanical findings go to the fix role as usual; release it when it ends. If deciding whether a design-level or subtle correctness finding agrees with the Spec, its tickets, or an ADR would require a judgment, run another Opus review (`--kind code` against the same fixed point, or `--kind diagnose` when presented as a failure record) and follow its findings rather than deciding in the flash session. The items under `## 需要人取舍` follow "Stopping" below: a `可自动采纳：否` or `推荐：无` item goes to one `opus-review.sh --kind draft` call, the items as its input with the Reversibility rule written at the top, and the Run applies that review's recommendation. The step-8 round cap applies here too: at most 3 review → fix → re-review rounds per review stream; after the third, mechanical-only leftovers land and are reported, and any correctness leftover parks with category `error`.
- **Step 9 conflicts**: resolve them with a fix role (step 9.1), but do not ask the user whether the resolution needs review and do not review it in-session. Record the pre-merge `spec-<n>` tip, then run `opus-review.sh --kind code --input <pre-merge spec-<n> tip> --out <run dir>/opus-conflict-review.md --cwd <integration worktree>`. Follow its findings: clean → continue; findings → one fix role, tests, and another code review of the conflict resolution. Release each role when it ends.
- **Two consecutive failures**: count failures per role and ticket. On the second consecutive failure, before re-briefing again or asking the user, write a failure record outside the repo containing the role, ticket, both sidecars and report paths, the relevant error tails, and what the gate observed; then run `opus-review.sh --kind diagnose --input <failure-record> --out <run dir>/opus-diagnosis.md`. Continue, change the Brief, or stop exactly as the findings direct.
- **Stopping**: the flash session decides nothing itself; it must not invent its own trade-off or parking decision, and must not settle an item by its own reading, not even one that looks answered by the Spec (on 2026-11-21 a flash session "ruled by the Spec" on two of five such items, one of which asked a human to check the Spec text Opus could not read). It acts only on Opus's own marks under `## 需要人取舍`: with `--auto-land`, an item with `可自动采纳：是` is applied as recommended and recorded under `### 自动拍板（可推翻）` (see Unattended landing); an item with `可自动采纳：否`, `推荐：无`, or no `可自动采纳` line goes to one Opus review (`--kind draft`, as "Step 8 findings" says) and the Run applies its recommendation the same way, recording it with the review's reason — only an item that review marks as needing the owner's identity or credentials parks, with category `auth` (its parking report's `### 需要你决定` copies that item as written), and a `推荐：无` from it means no reversible option: park with category `error`. Without `--auto-land`, relay every item to the user as written. This does not limit error stops below.
- **Opus review errors**: 退出码为 3（额度或 429）时按 quota 停车，2（认证失败）按 auth 停车，4 按 transient 停车，其余非 0 退出码按 error 停车并说明（退出码含义见 scripts/opus-review.sh 头注释）。Do not retry automatically, downgrade to GLM, or review in-session; the Stage route below is applied by `opus-review.sh` on every call, never by you. A quota park carries 停车类别 `quota` and the reset time as 可恢复时间, a transient park 当前时间 + 30 分钟, so keeper resumes both automatically; an auth or error park carries `无`.
- **Stage route**: `scripts/stage-route.sh`, which only the user runs (as `/grill-router`), holds the global Stage route table (GLOSSARY.md, ADR 0004): which Launcher profile, model and reasoning effort each stage runs on. `opus-review.sh` reads the `review` route on every `--kind code` / `draft` call and the `diagnosis` route on every `--kind diagnose` call, so a Run that is already executing changes model at its next review; the launcher, `--model` and `--effort` all come from the route. Every findings file starts with a `路由：审查（review）claude-glm / glm-5.4 / medium · <time>` line naming the route that produced it, and when the profile is not `claude` the wrapper's stderr says official Opus was not called. Act on the findings exactly as on any other, whatever the route: never change the route table yourself, and never reject findings because you take the switch for a downgrade — the route is the user's decision.
- **Dispatch route**: every dispatch reads the same route table afresh (see "Stage route" under "Headless executor"): the 实现 route for the interactive roles — the module refuses a `codex-glm` 实现 route as a usage error, exit 64, since codex on GLM runs only headless — and the 调研起草 route for the step-2 exploration. Each sidecar records the route it took, which is what the reports read. Never change the table yourself: only the user runs `/grill-router`.
- **Reports**: in both the final report and an Unattended-landing report, give every conclusion the path of the findings or role result that supports it (for example `<run dir>/opus-code-review.md`, `<run dir>/opus-diagnosis.md`, a dispatched role's report — its sidecar's `worker_done.report_path` — or the exploration's `research/result.md`). Require every role to write its final report to a durable file. Omit a conclusion for which no such path exists.

## Dispatching a role (the dispatch module)

Every implementing role — a Ticket's implementer, the fix role, a merge-conflict role — is an Orca worker started by `scripts/stage-dispatch.sh` (GLOSSARY.md "Sidecar", "Lean start"): a terminal in a worktree running the 实现 route's launcher with its model and effort, adopted by Orca (`worker-start --terminal`) into this Run's Orca Run (step 0). It sees none of this conversation: everything it needs must be in its Brief or reachable from it. One command dispatches, one waits, one releases; nothing else starts, checks or cleans up a worker, and the module's header (`scripts/stage-dispatch.sh`) is authoritative for every flag and exit code.

**Dispatching:**

1. Write the Brief, fresh for every worker (`<Spec Run root>/briefs/<name>.md`, from `find-next/templates/brief-implement.md`; do not derive one Brief from another with `sed` or search-and-replace — ticket numbers and branch names get left behind). Products only: the Spec issue's content, the exploration notes that concern this Ticket (the files and call relations), the Ticket issue's content, the repo's real test command, and the rules for its role — never this session's reasoning, attempts or messages (ADR 0004: each layer of session carries only the previous layer's products). For a fix role the context pointer is the review report; for a conflict role, the conflicted paths. **Brief 卫生**：往 Brief 里引用仓库外的文件（调研文档、别处的笔记、`~/ops` 下的脚本这类）前，先用系统索引（macOS 的 `mdfind`）或 `ls` 定位到确切路径并确认存在再写；定位不到就在 Brief 里明写「未定位到，不作为依据」，不给模糊路径让 worker 自行全盘搜索。各 Brief 模板的「环境约束（找文件与子进程）」一节是 worker 侧的对应约束。
2. Dispatch with one command; it prints the sidecar path, which is how the dispatch is addressed from here on:

   ```bash
   <skill dir>/scripts/stage-dispatch.sh dispatch --stage implementation \
     --role implement --ticket <m> --brief <brief file> --run <Orca Run id> \
     --run-dir <Spec Run root> --parent-worktree <integration worktree> --base-branch spec-<n> \
     [--mcp-config <file>] [--attempt <n>]
   ```

   `--role fix` (no `--ticket`) and `--role merge --ticket <m>` work in the integration worktree itself on the integration branch, and `release` leaves that worktree alone; `--role implement` gets a child worktree off the integration branch (a child does not inherit its parent's branch, so the base is always named). `--attempt <n>` (2 and up) names a re-brief: the module never overwrites an earlier sidecar. `--mcp-config` is for ops tickets. Exit `0` → the sidecar path on stdout. `64` → usage, among it an 实现 route the module cannot run interactively (`codex-glm`) or a `--run-dir` inside the Spec worktree: nothing started and nothing left behind — a route problem names the reset command (`/grill-router use implementation=claude-glm/glm-5.4/high`), and once the route is back the same command dispatches again under the same name. `6` → a prerequisite is missing (node, the route's launcher) or Orca failed. A refusal before the sidecar was written (the launcher missing, a directory that could not be made) leaves nothing behind either: fix it and dispatch again under the same name. Once a sidecar exists the stderr names what was created — a sidecar without `dispatch_id` did not complete, so clean it up (item 5) and dispatch again with `--attempt 2` (its sidecar stays, so the same name would be refused as taken). Never more than `GLM_MAX_PARALLEL` implementation workers at once (or the run's `--parallel` override).
3. Wait with one blocking call, never a polling loop: `<skill dir>/scripts/stage-dispatch.sh wait --sidecar <file> [--timeout <seconds>]` — one `check --run --take --types worker_done --wait`, default 7200 s. Run it in the foreground with a Bash `timeout` above the wait's own; when several workers run, wait on them one after another (each wait records every `worker_done` in the batch it took, so a wait woken by another Ticket's `worker_done` loses nothing, and a wait on a dispatch whose `worker_done` was already recorded returns at once). Exit `0` → stdout is the report path; the sidecar's `worker_done.outcome` says `succeeded` or `failed`. `5` → timed out: not a verdict — ask Orca (`worker-show`) and the Watchdog, then wait again or act as the Watchdog says. `7` → woken by another dispatch's `worker_done` (recorded in that sidecar): wait again. `8` → the wait took mail of this Run that is no `worker_done` (a Ticket worker asking its Spec session; each message is a line of JSON on stdout, the batch kept in the dispatch dir's `wait.json`): answer it (`orca orchestration send --run <run id> --to dispatch:<its dispatch id> --subject … --body …`), then wait again. `6` → Orca failed: nothing was lost that Orca still holds, wait again; `6` also covers a `worker_done` whose report is not on disk — then do not wait again (a further wait returns at once with a path that does not exist): handle it as `5` above (ask Orca, `worker-show`), and a worker that is done with no report is a ticket whose work is incomplete — release it and re-dispatch as in step 5's exit-`2` line.
4. Verify (the gate below), merge (step 5), and **release as soon as the role is over**: `<skill dir>/scripts/stage-dispatch.sh release --sidecar <file>` — `worker-release`, the terminal closed, and a child worktree removed with its branch; a fix or merge role's integration worktree is kept. Release refuses (exit 2) a worker that has not reported or is not settled: its report may still be coming. A report the worker wrote inside its worktree is copied out to the dispatch dir first (`report-from-worktree.md`), so nothing is lost with the worktree. Before the terminal closes, release also reads the model the worker actually ran on off its terminal and records it in the sidecar (`actual_model`) — Orca records none for an adopted terminal, and the reports print it through `stage-dispatch.sh verify --run-dir <Spec Run root>` ("Report at the end"); whatever it read, release goes on.
5. A dispatch that did not complete, or a worker that ended without a `worker_done` (stopped, or exited on its own), cannot be released (exit 2): clean up by hand what its sidecar names — `orca terminal close --terminal <terminal> --tab`, then `orca worktree rm --worktree path:<worktree> --force --delete-branch` for a child worktree (never the Spec worktree) — keeping any report that was written.

**Lean start.** By default the implement and fix roles start with the route's launcher `--bare --append-system-prompt-file <rules> [--mcp-config <file>]` (ADR 0004: a trivial task goes from 18.6K to 1.2K input tokens): no CLAUDE.md, skills, plugins or hooks are loaded, so the rules they must follow come from the rules file (`ISS_DISPATCH_LEAN_RULES`, default `templates/lean-rules.md`, which #39 settles) and from the Brief, and the MCP servers a Ticket needs come from `--mcp-config`. Until that file exists the start is a normal one, with skills and hooks loaded; `ISS_DISPATCH_BARE=0` turns the lean start off; the merge role never starts lean, since it resolves conflicts on the integration branch where CLAUDE.md and the hooks must stay. The sidecar's `bare` and `bare_note` say which start a worker got. A rule that was a hook's hard block (writing source, pushing, asking a person) is a prompt rule for a lean worker, backed by the gate before a merge and by review (step 7) — so write every rule the worker must keep into its Brief, and trust the scripts, not its report.

**Verification gate** (implementers and fix). Never trust the worker's report alone. All must hold, and the first three are scripts':
- new commits — for an implementer `merge-ticket.sh`'s gate (exit 2 names the miss; exit 5 means the branch has already landed, which step 5 handles): at least one commit on `spec-<n>-t<m>` that the integration branch lacks; for fix, `git rev-list --count <pre-fix tip>..spec-<n>` is ≥ 1;
- a clean tree — `merge-ticket.sh` checks both worktrees; for fix, `git status --porcelain` is empty in the integration worktree;
- the merger script's test run passes — step 5's exit 0; for fix, the test command run in the integration worktree after it;
- the sidecar's `worker_done.outcome` is `succeeded` and its report is on disk.

If any check fails, re-brief once (`--attempt 2`) with what is missing; if it still fails, ask the user. Review (step 7) is the backstop for what no script can check.

## Headless executor (`scripts/codex-worker.sh`)

The one headless executor in this skill: a wrapper script (in this skill's directory) running one `codex exec` process on GLM, inside a worktree, with a Brief. It runs the step-2 exploration (`--read-only`, the 调研起草 route) and find-next's research, decision and drafting workers; the implementing roles are never run by it. It sees none of this conversation: everything it needs must be in its Brief or reachable from it.

- `<worker>`: `scripts/codex-worker.sh`; its model and reasoning effort come from the Stage route table (`/grill-router`; default `glm-5.4`, effort `high`) and are never passed as `--model`.
- preflight: `scripts/selftest-codex.sh --only L1` (dispatches on the implementation stage's effective route). Its usual failure is the local proxy not running (the preflight address is derived from the `base_url` in `config.toml`; author environment: Ferryman, `127.0.0.1:15722`), its key, or the routed model not being served.

**Stage route** (ADR 0004; GLOSSARY.md "Stage route"). The model and reasoning effort of every `codex` headless run — the step-2 exploration, find-next's research, decision and drafting workers, and the everyday hand-offs of the global Opus / codex division alike — come from the user's Stage route table, `scripts/stage-route.sh` (`~/.claude/state/stage-route`): the `research` stage for a dispatch with `--read-only`, the `implementation` stage for every other. Both default to `glm-5.4` with effort `high`. `codex-worker.sh` reads the table on every fresh run, so a Run that is already executing changes model at its next dispatch; a Resume keeps the model, effort and profile of its first segment. Priority: the stage's route when it is off its default, then an explicit `--model` / `--thinking`, then the default route. Do not pass `--model` or `--thinking` (an older version of this file did): while the stage is off its default they are overridden, and the wrapper says so with one line on stderr, also appended to the run dir's `stderr.log` — every dispatch names its stage and route there; off the default the line also names any overridden `--model` / `--thinking`, the expiry and the reset command, and it notes a model the worker home's catalog does not list. `status.json` and `resume.json` record the route in effect, as the table names it: the `profile`, `model` and `thinking` (the effort). Every codex worker runs through codex-glm whatever profile the route names and takes only the route's model and effort, so `profile` is the table's entry (the default route's `claude-glm`), not the launcher that ran. When that line says a route is in effect, read `status.json`'s `model` and `thinking` to know what a worker really ran on, and say so in the landing report and the final report. A route whose model or effort codex-glm does not take (an effort of `max`, for example) is a usage error: the wrapper exits 64 without starting codex and names the route and its reset command. Never change the table yourself: only the user runs `/grill-router`.

**Preflight** (once per Run, before step 2): run the executor's preflight command from the table (prefixed with `<skill dir>/`). If it fails, stop and show the user the error, and name the route's current value and the reset command (the value is what `scripts/stage-route.sh` prints; the reset is that stage's line after 切回用, e.g. `/grill-router use implementation=claude-glm/glm-5.4/high`): the preflight dispatches on the implementation stage's effective route, so a failure may mean the routed model is not served, and this is the only stop before the first dispatch that can say so. Also note the local time: weekdays 14:00–18:00 Beijing time are GLM peak hours (GLM-5.x quota is charged 3x and 429s are more likely). Proceed anyway; just mention it in the final report.

**Dispatching the exploration.** Step 2's one command runs the executor in the foreground through the module:

```bash
<skill dir>/scripts/stage-dispatch.sh dispatch --stage research --brief <brief file> \
  --run-dir <Spec Run root> --cwd <integration worktree> [--mcp all] [--attempt <n>]
```

It never calls `codex-worker.sh` by hand: the module reads the route and writes the sidecar the reports read. It exits with the wrapper's own exit code and prints the report path; the run dir is `<Spec Run root>/research/` (`brief.md`, `result.md`, `status.json`, `events.jsonl`, `stderr.log`). No `--model` or `--thinking` — the Stage route decides both — and no `--skill` or time limits: the module passes none, so the wrapper's defaults apply. Set the Bash `timeout` above the wrapper's Time limit (1800 s by default). MCP is disabled by default: an exploration that needs internet search adds `--mcp all`. The wrapper first takes one of the machine-wide Worker slots (`ISS_MAX_WORKERS`, default 4, shared by all Runs and all repos, since they share one GLM quota); while it waits, its run dir has a `queued` file and `progress.sh` shows `queued`, and the wait does not count against the Time limit — do not treat a queued executor as stuck. Never ask it to delete directories recursively: codex refuses `rm -rf` / `Remove-Item -Recurse` even without a sandbox. To see what it is doing — when the user asks, or it runs long — run `<skill dir>/scripts/progress.sh <Spec Run root>/research`: state (`running` / `finished` / `dead`), seconds since its last progress, the command in flight, recent commands, edits and messages, tokens. Look when needed; do not poll it in a loop (the wrapper's own watchdog handles stuck workers). `dead` means the wrapper is gone without writing `status.json` (e.g. the session that launched it ended): treat it like `error`. When it exits, read `status.json` and `result.md`; do not read `events.jsonl` unless debugging a failure.

**Exit codes / `status`** (the executor's own; `scripts/codex-worker.sh`'s header is authoritative):

- `0` / `ok`: the executor finished without an API error. This is not success yet: apply step 2's gate.
- `8` / `violation`: a `--read-only` exploration changed the workspace. Do not trust its notes; inspect `status.json`'s `changed_paths`, revert them by hand, and dispatch again with `--attempt 2` (a second violation parks an unattended Run).
- `2` / `auth`, `3` / `quota`, `4` / `transient` (already retried by the agent and by the wrapper): the GLM side is unusable right now. Stop dispatching, let running workers finish, and apply the Unattended-landing rules (or ask the user): wait and retry, or pause. There is no other backend to switch to.
- `5` / `timeout`: the executor reached its Time limit; the codex thread is kept and can be **Resumed** (GLOSSARY.md). Read the tail of `stderr.log` and `result.md` if any, then check `status.json` for progress. With progress (notes already written), Resume it once — same run dir, same session, no new Brief:

  ```bash
  <skill dir>/scripts/codex-worker.sh --resume --run-dir <Spec Run root>/research
  ```

  The wrapper reads the worktree, model, thinking level, MCP selection and session from the run dir; never pass `--cwd`, `--brief`, `--model`, `--skill`, `--thinking`, `--add-dir` or `--mcp` to a Resume. On a second `timeout`, or a first one with no progress, do not Resume again — ask the user (an unattended Run parks).
- `6` / `error`, `7` / `stalled`: the executor failed (`stalled` = the Idle timeout fired: no progress events for the wrapper's Idle timeout, so the session is stuck — do not continue that session). Read the tail of `stderr.log` and `result.md` if any. Re-brief once with `--attempt 2` and the failure appended; if it fails again, ask the user. In Flash mode, see "Flash mode".
  - Exception: a `stalled` whose `status.json` has a non-null `result_file` means codex already gave its final reply but never closed the turn (the wrapper saved that reply to `result.md`). Apply step 2's gate, accepting `stalled` in place of `ok`; if every other check holds, treat the exploration as done.
